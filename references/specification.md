# 需求规格与业务流程审查

## 理解现有项目

读取本次需求关联的入口、调用链、数据模型、测试和业务文档，定位足以说明当前行为的证据。控制阅读范围，不为一个局部需求盘点整个系统。新项目说明尚无实现基线。

规格中的当前行为用短句概括，必要时引用文档章节、代码路径或标识符。记录重要文档与代码冲突，交由需求目标决定；不要悄悄选其中一个当成已确认事实。无法访问代码时注明基于哪些材料生成，以及哪些现状尚未核实。

## 定义本次变化

先明确目标、变化范围和外部可观察结果。对于现有项目，突出“当前如何、目标如何”，只引用理解本次变化所需的背景。必须保持的兼容行为列为规则或验收条件，不重新描述整个模块。

关键问题尽早提出，给出影响和少量明确选项；不要把假设写成确定要求。对不影响业务含义的常规实现选择，可在后续设计中解决。未决问题只阻塞依赖它的部分，草稿可以保留未决事项。

## 编写可审查规格

使用 [精简模板](../assets/spec-template.md)，按实际需求保留章节。

- 主流程用 `F1` 等稳定编号，说明执行者、前置条件或动作、结果、状态及下一步。条件简单时合并表达，不追求表格复杂度。
- 分支异常用 `E1` 等编号并关联 `F` 步骤，说明触发条件、处理结果和最终状态。只有需求涉及重试、撤销、恢复等行为时才展开。
- 跨步骤或易被遗漏的约束集中为 `R1` 等规则。简单步骤可以直接定义其行为，无需再复制成一条规则。流程引用相关 `R` 编号即可。
- 验收用 `A1` 等编号引用流程或规则，只补充足以验证行为的输入、操作和预期结果。单纯写“符合 R1”不构成可执行验收。
- 涉及多状态流转、跨角色交互或分支难以扫描时，按 [diagrams.md](diagrams.md) 调用 `drawio-skill` 生成状态图、泳道图或流程图。图用于展示关系，详细规则仍只定义一次；简单关系或技能不可用时可用 Mermaid。
- 编号新增时延续已有编号，删除时移除引用或标出替代关系，不为整理版式大规模重新编号。

不要强制每个需求包含多个用户故事、优先级解释、独立测试说明和业务指标。用户确实需要故事或指标时，再加入有依据的内容。

## 审查流程合理性

沿用户操作和状态变化检查，而不是只检查标题是否齐全。关注与需求有关的项目：

| 关注点 | 要判断的问题 |
|---|---|
| 步骤衔接 | 输入从哪里来？结果到哪里去？每个分支是否有明确出口？ |
| 状态与角色 | 是否出现不可达状态、无出口状态或不允许的转换？谁能执行每一步？ |
| 规则一致性 | 相同条件是否产生矛盾结果？前后置条件、计算规则是否一致？ |
| 异常与恢复 | 失败后停在哪个状态？涉及重试时是否可能重复扣款、写入或通知？ |
| 数据与兼容 | 哪些数据改变？已有用户、历史数据或外部调用是否受到影响？ |
| 可验收性 | 是否能观察成功与失败？关键行为是否有可执行的验收条件？ |

报告真实问题，给出关联编号、触发条件、后果和待决策事项。区分确认的逻辑矛盾、尚缺的需求信息和可选优化，避免把偏好当成缺陷。

只审查时输出发现，不自动重写或实现。用户要求生成或修正规格时，可直接修正文档中明确的遗漏和重复；改变业务含义的修正仍需依据已确认需求。

## 阶段结束条件

规格草稿可以包含未决问题；进入设计或实现的部分应具有明确行为、闭合的关键流程和可验证结果。只生成规格时，说明它是否可进入下一阶段，并列出真正的阻塞项后结束。不要把未被用户确认的目标标成“已确认”。
