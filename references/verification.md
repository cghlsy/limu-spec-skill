# 验收、代码审查与完成判断

## 区分三类检查

- 业务流程审查检查预期行为是否合理，按 [specification.md](specification.md) 执行。
- 验收检查实际实现是否满足 SPEC，用运行结果或检查证据支持结论。
- 代码审查检查缺陷、回归风险和实现约束，可以发现验收未覆盖的问题。

用户只要求其中一项时，不强制运行所有阶段。单独审查可以报告问题并结束；完整交付中的明确实现缺陷应修复后做针对性复验。新的业务决策需澄清。

## 验收

读取 SPEC 中的验收要点，定位项目已有测试和检查命令。用风险决定验证力度：局部改动做聚焦检查；共享模块、接口或高风险业务增加相关集成和回归验证。按实际涉及情况检查异常、权限、并发、重复操作、历史数据和兼容行为。

每项记录结果和足够的证据，不把同一条规则全文再写一次：

| 编号 | 结果 | 证据或限制 |
|---|---|---|
| A1 | 通过 | 实际执行的命令、场景或证据位置 |
| A2 | 失败 | 观察到的结果、关联缺陷 |
| A3 | 未验证 | 缺少环境、凭证、数据或其他原因 |

只有实际执行并得到预期结果才能记为通过。只读代码检查时注明“静态检查”，不能替代运行时验收。一个自动测试覆盖多项验收时复用证据引用，不重复执行来填表。修复后只重跑受影响的检查及项目要求的必要检查。

## 代码审查

检查本次改动及足够的调用上下文，关注：

1. 实现与 `F`、`E`、`R` 的对应关系，是否遗漏分支或改变未经确认的行为。
2. 可触发的逻辑错误、状态问题、边界处理和相关权限或数据风险。
3. 对已有接口、调用者、数据和用户行为的回归影响。
4. 对关键行为有意义的测试缺口，以及对项目明确约定的违反。

不以文件数量、文档篇幅或个人风格作为质量指标。问题按严重程度排序，每项说明代码位置、触发条件、后果及适用的规格编号。缺少证据的疑问与确定缺陷分开。没有可确认问题时明确说明，并保留实际未验证的范围。

审查发现涉及复杂调用链、跨模块数据流、竞态时序或状态转换，图示能帮助解释触发路径和后果时，按 [diagrams.md](diagrams.md) 调用 `drawio-skill`。文字发现仍说明证据与代码位置，图示不能替代缺陷证据或运行时验证。已有 Markdown 审查报告中引用图示；没有报告时不为画图强制新建整套审查文档。

## 完成判断

用下列状态描述结果，不要求单独创建报告文件：

- **已完成**：用户要求的范围已交付，必要验证通过，没有阻塞完成的已知缺陷；适用的规格和设计与实现一致。
- **待验证**：实现已完成，但必要验收尚未执行或缺少环境；说明未验证项及原因。
- **未完成**：仍有失败验收、未实现行为、阻塞决策或必须修复的缺陷。

未决问题如果与本次完成范围无关，说明其范围而不是自动阻塞全部交付。可选优化不等同于必须修复的缺陷。验证通过不意味着覆盖所有可能行为，按已执行的证据说明实际结论。

如果项目维护 SPEC，在原文的“验收与完成记录”中简要更新证据和遗留问题；保留验收定义，更新最近结果，避免累计重复报告。只做只读审查或用户不要求修改文档时，在对话中报告即可。
