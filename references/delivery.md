# 技术设计与开发实现

## 从现有规格开始

读取当前 SPEC 以及用户已接受的决策。若缺少规格，根据入口规则确定直接处理、先补简版还是先澄清需求。已有规格足够时不重新生成。用户只要设计时，完成设计后结束；完整交付请求不强制增加阶段审批。

## 设计必要的内容

先检查现有模块、接口、依赖和测试惯例，复用适合的做法。技术方案聚焦变化：

- 修改哪些模块，如何实现相关 `F`、`E`、`R` 行为。
- 接口、数据、状态或兼容性是否变化。
- 重要技术决策及理由；只有存在实际取舍时才比较方案。
- 需求涉及迁移、并发、外部失败或难回退操作时，说明相应措施。
- 用什么检查验证关键行为，复用已有测试入口。

小需求在 SPEC 中写几个要点即可。复杂设计拆到同目录 `design.md`，在 SPEC 中只留下链接和必要结论。不要复制需求全文、全部项目目录或无关技术栈介绍。

跨模块调用、异步交互、数据流或架构边界难以用文字说明时，按 [diagrams.md](diagrams.md) 调用 `drawio-skill` 生成相应图示，在方案中引用。方案或需求变化影响图中关系时，同步更新对应图示。

## 组织实施

根据实际依赖安排工作，不为每个需求强制生成任务文件。任务描述可使用如下最小格式：

```markdown
- [ ] T1：修改导出查询，复用权限过滤（R2）；验证 A1、A3。
- [ ] T2：处理下载失败提示（E1）；验证 A2。
```

需求编号只用于追溯，任务还应说明具体工作和验证目标。多人协作或任务依赖难以管理时才拆 `tasks.md`。完成状态随着工作更新，不在结束时批量标记未验证任务。

在用户指定的项目和范围中实施；读取正在修改的文件，保留已有改动。按照风险补充有价值的回归测试，尤其是原缺陷、边界行为和共享契约，不为低影响改动创建镜像实现的测试。

## 实现中的发现与需求变更

区分发现的性质：

| 发现 | 处理方式 |
|---|---|
| 纯实现选择变化 | 更新必要的方案或任务，保持目标行为 |
| 当前行为与规格中的现状不符 | 修正现状记录，评估对目标和兼容性的影响 |
| 需求存在关键歧义或不可实现的约束 | 说明证据与选项，澄清受影响行为，继续独立工作 |
| 用户明确改变目标 | 更新规格正文，检查方案、任务、代码和验收受影响的部分 |

不要通过“实现备注”悄悄修改业务规则，也不要重新生成全部文档丢失已确认决策。必要时仅记录一条重要变更理由；不要求独立变更日志。

## 交付前衔接

实现完成后，在用户要求的范围内进入 [验证与代码审查](verification.md)。完成摘要关联具体改动与验收结果。代码编译成功或任务勾选完成，都不能单独证明需求已满足。
